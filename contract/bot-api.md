# FoxFleet Bot API, protocol `foxfleet.bot/1`

Status: **experimental, default off**. The hub only exposes anything described here when it runs with
`FOXFLEET_BOT_API=1` (or `createHub({ botApi: true })`). With the flag off, every route below answers as if it did not
exist and saved bot agents fail safe (shown offline, never routed anywhere else).
`FOXFLEET_BOT_AGENTS=a,b` (0.3.12, `createHub({ botAgents })`) limits the API to those agent names: any other bot
agent cannot be created or mint a token (403) and its token authenticates nowhere (401). **Deny by default:** unset or
empty = no bot agent at all (the hub logs a warning at start); `*` = every bot agent.
Rollout/rollback runbook: `docs/BOT-API-ROLLOUT.md`.

The hub acts as a small chat server (Telegram-Bot-API style). A *bot* is a program, normally the future
Hermes `foxfleet` platform adapter, that dials **out** to the hub over one WebSocket, receives
the messages people send it, and answers with plain requests. The hub keeps the transcript; the bot keeps nothing that
the user's apps need.

Machine-readable frame examples: `contract/bot-frames.vectors.json` (checked by `server/test/bot-contract.test.js`).

## 1. Scope of v1

Implemented in this version, and nothing else:

| Area | Implemented |
|---|---|
| Registration | `POST /api/connections` with `connection: "bot"` |
| Tokens | mint/rotate `POST /api/agents/:name/bot-token`, revoke `DELETE /api/agents/:name/bot-token` |
| Socket | `GET /api/bot/ws` (WebSocket), one live connection per bot |
| Standalone bot requests | `POST /api/bot/rpc` (non-displacing HTTP, send/edit/delete/typing only) |
| Hub → bot | `hello`, `message.new`, `res`, `error`, `ping`, `pong` |
| Bot → hub | `ack`, `ping`, `pong`, `message.send`, `message.edit`, `message.delete`, `chat.action` (`typing`), `commands.set`, `models.set` |
| User side | the existing agent routes: list/detail, sessions, transcript, `/messages`, `/chat`, `/runs`, `/queue`, `/commands`, `/models`, `/pin`, `/reactions`, `/hidden` |
| Content | text only, direct chats (`chat_type: "dm"`) |

**Reply conventions (0.4.2).** A bot reply's `REACT: <emoji>` line is not shown as text: the hub
removes the line from the stored message and, on the reply's `final` frame, records the emoji as the
agent's reaction on the user message that started the turn (announced as a `message.reaction` live
event). A reply that is only a `REACT:` line keeps the emoji as its text so the turn still ends.
`sessions/{id}/reactions` and `sessions/{id}/hidden` work for bot chats on the bot store's `fm_`
message ids, with the same request/response shape as the other agents.

**Thinking (0.4.2).** `message.send` and `message.edit` accept an optional `reasoning` string (the
turn's thinking, capped at 64 KiB). The hub keeps it with the reply (`reasoning` in the transcript)
and streams it on the reply's run as `foxfleet.reasoning` events whose `text` is the whole thinking
so far (the client replaces its block, so replays and revisions converge). A bot that sends none is unchanged.

An empty native stream is closed by Hermes with a lone `✅` finalize frame. The adapter stores that
tick non-final so the turn stays open: the authoritative text (if any) then replaces that message,
and with no text the tick stays as the answer. Only the turn's own answer may replace it; notice/interim sends are separate messages.

Reserved names, **not implemented** (frozen so later versions do not collide). A bot that sends one gets
`error.code = "unsupported"`; the hub never emits the hub → bot ones in v1:

- hub → bot: `message.edited`, `message.deleted`, `callback`, `reaction`, `replay.gap`, `chat.member`
- bot → hub: `message.react`, `callback.answer`, `media.upload`, `card.send`, `chat.get`, `chat.cancel`
- fields on `message.send` / `message.edit`: `media`, `buttons`, `keyboard`, `card`, `thread_id`, `group_id`,
  `parse_mode`, `silent`, `reactions`
- `chat_type` values `group`, `thread`
- HTTP: `POST /api/bot/media`, `GET /api/bot/media/:id`

Callback strings, card data and button payloads authorise nobody and are never accepted in v1.

## 2. Registration and ownership

A bot is one agent record of kind `hermes` with `connection: "bot"`, owned by exactly one hub account: the account whose
registry holds it (the hub owner's own registry, or a member's per-account registry). Every authenticated account may
register bots in **its own** registry, exactly as it may add direct agents there; nobody can see, mint for, or talk to a
bot in another account's registry (it answers `404 Unknown agent`).

```
POST /api/connections            (session auth: cookie or Bearer, same as every /api route)
{ "kind": "hermes", "connection": "bot", "name": "helper", "label"?: "...", "description"?: "...", "avatar"?: "..." }
→ 201 { "connection": { "name": "helper", "kind": "hermes", "connection": "bot", "profile": "default",
                          "botId": "<24 hex>", "hasBotToken": false, ... } }
```

- `botId` is generated by the hub (any value sent by the client is ignored), never changes, is not a secret, and is
  the `bot` value in `hello`.
- No host, port, URL, dashboard or API credential is needed or stored for a bot. Such fields are ignored.
- `connection` cannot change on edit (`PUT /api/connections/:name` may change `label`, `description`, `avatar`).
- With the flag off, `connection: "bot"` is rejected exactly like any unknown mode (`400 Invalid connection mode`).

### Tokens

```
POST   /api/agents/:name/bot-token   → 201 { "token": "ffb_<43 base64url chars>", "bot_id": "...", "created": <ms> }
DELETE /api/agents/:name/bot-token   → 200 { "ok": true }
```

- Token = `ffb_` + base64url(32 random bytes). It is returned **once**. The hub stores only `sha256(token)` (hex) in
  `<data>/bot/tokens.json` (mode 0600). No API response, list, log line or error ever contains a token or its hash;
  `GET /api/connections` and `/api/agents` expose only `hasBotToken` (boolean).
- `POST` rotates: the new hash replaces the old one on disk **before** the response is sent, the old token is rejected
  from then on (restarts cannot revive it), and the bot's live socket, if any, is closed at once with code `4001`.
- `DELETE` revokes the same way. `404` for an unknown agent or one in another account; `409` if the agent is not a bot.
- Deleting the agent (`DELETE /api/connections/:name`) revokes its token, closes its socket with `4003`, ends its live
  runs and deletes its bot store file. Removing the owning account revokes all of its bots; disabling the account
  closes their sockets (`4003`) and rejects new ones until re-enabled.
- Once a rotate, revoke, agent delete or owner disable has been answered, no further write from the old connection is
  applied. A write that is already committing finishes before the answer is sent; requests of that connection not yet
  applied are refused. The same holds for a connection replaced by a newer one (`4009`): its not-yet-applied requests
  are refused.

## 3. Transport

```
GET /api/bot/ws HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Version: 13
Sec-WebSocket-Key: <base64 16 bytes>
Sec-WebSocket-Protocol: foxfleet.bot.v1
Authorization: Bot ffb_...
```

Admission, in this order (failures answer a plain HTTP status and close; no WebSocket is opened):

| Check | Failure |
|---|---|
| flag on and path is exactly `/api/bot/ws` with **no query string** (tokens never travel in URLs) | 404 / 400 |
| hub host boundary (same rules as every request) and no foreign `Origin` header (only a trusted hub origin may appear) | 403 |
| transport security: the socket peer is loopback **and** either the `Host` is loopback or `X-Forwarded-Proto: https`; or `X-Forwarded-Proto: https` with a `Host` listed in the hub's trusted HTTPS origins. Plain HTTP from the network is refused so a token never crosses it in clear | 403 |
| valid WebSocket handshake, and `foxfleet.bot.v1` offered in `Sec-WebSocket-Protocol` (the hub echoes it) | 400 |
| per-IP auth throttle (shared with logins): an IP already over the limit is refused; only a **failed** credential spends it (0.3.12) | 429 |
| `Authorization: Bot <token>` well formed, hash known, owning account exists and is enabled, agent still exists with that `botId` and `connection: "bot"` | 401 (same answer for every reason) |
| per-bot connect bucket for authenticated upgrades (default burst 20, refill 20/min; `botOptions.connectBurst` / `connectPerMin`), so a reconnect loop is slowed without touching the login budget (0.3.12) | 429 |
| the bot's store is readable | 503 |

Identity comes **only** from the token: it binds (account, botId). Ids inside frames are never authority; every chat or
message id a bot sends is looked up inside that bot's own store.

**One connection per bot.** A newly admitted connection replaces the old one, which is closed with `4009`.

### Non-displacing HTTP requests

For cron and standalone `send_message` calls, use **`POST /api/bot/rpc`**, not a temporary WebSocket.
This is a non-displacing request transport: it never opens a socket, sends `hello`, acquires a receive lease,
replaces an existing connection, changes event delivery/ack state, or marks an offline bot online.
User-message delivery still requires the long-lived WebSocket. Machine vectors:
`contract/bot-http.vectors.json`, exercised against the real hub by `server/test/bot-http-contract.test.js`.

```http
POST /api/bot/rpc HTTP/1.1
Authorization: Bot <token>
Content-Type: application/json

{"t":"message.send","id":"cron-1","chat_id":"fc_…","text":"Scheduled reply","final":true,"idempotency_key":"cron:job:run"}
```

- Body is exactly one normal bot request frame. Only `message.send`, `message.edit`, `message.delete`, and
  `chat.action` are allowed. Field validation, default format/final, ownership, caps, transcript/activity and reply-run
  behavior are the same as on WebSocket. Explicit `final: false` keeps the run open; `final: true` ends it.
- `ack`, `ping`, `pong`, `commands.set`, `models.set` and reserved operations return `unsupported`; unknown operations return
  `unknown_type`. No polling, commands registration, media, buttons, groups or receive protocol is added here.
- The token is the only account/bot/agent authority. Such fields in the body are rejected, not used for routing.
  The path is exactly `/api/bot/rpc`: no trailing slash, query string (even an empty `?`), URL tokens or redirects.
  Clients must disable redirect following when sending credentials.
- Same host/origin boundary and transport-security rule as socket admission. The per-IP auth throttle (shared with
  logins) is spent only by **failed** bot authentication; an IP already over that limit is refused (429) even with a
  valid token. Authenticated requests never spend it: they are bounded by the per-bot rate bucket instead. Browser-style
  cross-site requests are refused. Native clients can omit `Origin`; published proxy hosts must be explicitly trusted.
- One **shared per-bot rate bucket** across HTTP and WebSocket. Idempotency keys and durable stores are also shared
  across transports and hub restarts. Replays do not duplicate activity or start a new run. A valid HTTP call can work
  with no socket; it does not affect the current socket's probe status or connection ownership.
- HTTP authorisation is rechecked after async admission/body reading and inside each queued store mutation, including
  replay attempts. Deleted agents/accounts, disabled accounts and rotated/revoked tokens cannot apply pending writes.
  Disabling then re-enabling an account does not revive its already admitted HTTP requests. An already committing
  write completes before management answers, as with WebSocket.
- One encoded request body is at most **1 MiB**, text at most **65 536 UTF-8 bytes**. JSON must be valid UTF-8.
  Errors never echo arbitrary field names or request payloads; response fields are bounded, correlation ids at most
  64 characters. No token or hash is returned by this endpoint.

| HTTP status | Meaning |
|---|---|
| 200 | A `res` envelope, including protocol/ownership/rate/idempotency errors: `{t:"res",id,ok,result\|error,replayed?}` |
| 400 | Malformed/empty JSON, invalid UTF-8, or non-exact request target/query string |
| 401 | Missing/invalid/revoked/rotated Bot token, disabled/deleted owner or agent; also when an admitted queued request loses authorisation |
| 403 | Host/origin/cross-site or transport-security boundary refusal |
| 404 | Feature flag off, or non-POST method (no redirect) |
| 413 | Encoded request exceeds 1 MiB (declared or streamed) |
| 415 | A body with a non-JSON Content-Type (the shared hub mutation boundary) |
| 429 | The IP is over the shared per-IP auth throttle (spent only by failed authentication); per-bot rate errors instead use HTTP 200 `res.error.code = "rate_limited"` — over HTTP every authenticated request costs one bot token and rate-limited envelopes always carry `id: null` because the frame is not read |
| 503 | Token index/bot store unavailable, or hub shutting down |

All admitted, syntactically valid JSON frames get a `res` envelope, even if the JSON value is not a frame object.
A valid `id` is echoed; **id: null** means no valid correlation id was supplied. This differs from the socket's bare
`error` frame/close behavior. Error envelopes contain `error: {code,message,retry_after_ms?}`; successful envelopes
contain `result`, with `replayed: true` only for an idempotent replay. HTTP responses are `Cache-Control: no-store`.
Authentication/boundary/JSON/store HTTP failures use the hub's ordinary `{error,code?}` shape instead of `res`.

### Frames

- Text frames only, each one JSON object with a string field `t`. Client frames must be masked; RSV bits must be 0
  (no extensions); fragmented messages are reassembled; control frames must be final and ≤ 125 bytes.
- Size: one message (all fragments together) ≤ **1 MiB**; a larger declared length closes with `1009` before the body
  is buffered. Text fields have their own caps (below).
- Binary messages close with `1003`, invalid UTF-8 with `1007`, framing errors with `1002`.
- Not JSON, not an object, or no string `t`: `{"t":"error","code":"bad_frame"}` then close `1008`.
- Unknown `t`: `{"t":"error","code":"unknown_type"}`; reserved `t` (section 1): `res`/`error` with `unsupported`.
  The connection stays open.
- The hub processes a connection's frames strictly in order. While more than 64 received messages wait, it stops
  reading the socket (TCP back-pressure). If more than 8 MiB of hub → bot output is buffered (a bot that does not
  read), the hub closes with `1013`; nothing is lost because events stay in the store until acknowledged.

### Heartbeat

The hub sends a WebSocket ping every `heartbeat_ms` (default 25 s) and answers pings. The bot may also send
`{"t":"ping","id"?}` → `{"t":"pong","id"?}`. If the hub receives no frame at all for 3 × `heartbeat_ms`, it closes with
`1001`.

### Close codes

| Code | Meaning |
|---|---|
| 1000 | normal |
| 1001 | hub shutting down, or idle timeout |
| 1002 / 1003 / 1007 / 1009 | WebSocket protocol error / binary message / invalid UTF-8 / message too big |
| 1008 | frame is not a JSON object with `t` |
| 1011 | internal error |
| 1013 | bot does not read fast enough |
| 4001 | token rotated or revoked |
| 4003 | agent deleted, owner removed or disabled, or bot API turned off |
| 4009 | replaced by a newer connection of the same bot |

## 4. Hub → bot

### hello (first frame on every connection)

```json
{ "t": "hello", "protocol": "foxfleet.bot/1", "bot": "<botId>", "resume_from": 41, "latest_event_id": 44,
  "heartbeat_ms": 25000,
  "limits": { "max_frame_bytes": 1048576, "max_text_bytes": 65536, "window": 100, "max_unacked": 1000 } }
```

`resume_from` is the bot's persisted cumulative ack; every event with a larger id that still exists is delivered next,
in order, without the bot asking.

### message.new (durable event)

```json
{ "t": "message.new", "event_id": 42, "chat_id": "fc_…", "chat_type": "dm", "message_id": "fm_…",
  "user": { "id": "<hub account id>", "name": "<username>" }, "text": "hello", "date": 1760000000000,
  "reply_to"?: "fm_…" }
```

`user` always comes from the authenticated hub session that sent the message, never from request bodies.

### res / error

```json
{ "t": "res", "id": "<request id>", "ok": true,  "result": { … }, "replayed"?: true }
{ "t": "res", "id": "<request id>", "ok": false, "error": { "code": "not_found", "message": "…", "retry_after_ms"?: 500 } }
{ "t": "error", "code": "bad_frame", "message": "…" }
```

`error` is used only when there is no valid request id to answer.

## 5. Delivery, acknowledgement, replay

- Event ids are positive integers, strictly increasing per bot, never reused (the counter is persisted).
- Delivery is **at-least-once**, not exactly-once: after a reconnect or a hub restart every event above the persisted
  ack is delivered again. Bots must de-duplicate by `event_id` (or `message_id`).
- Flow control: at most `window` (default 100) delivered-but-unacknowledged events per connection; more follow as
  acks arrive.
- `{"t":"ack","event_id":N,"id"?:"…"}` is cumulative ("everything ≤ N is handled").
  - `N` must be a non-negative safe integer and ≤ the highest event id **delivered on this connection**; otherwise
    `ack_out_of_range` (no state change). Acknowledging an event the hub has not sent yet is an error.
  - `N` ≤ the current ack is a harmless no-op.
  - Otherwise the new ack is written to disk **before** success is reported (`res` with `{"acked":N}` if the ack had an
    `id`), and the acknowledged events are then dropped from the store.
- **Admission instead of loss.** The hub never drops an unacknowledged event. When a bot already has `max_unacked`
  (default 1000) unacknowledged events, a new user message is refused: `503` with `code: "bot_backlog_full"` and
  `Retry-After`. Nothing is written in that case.
- `replay.gap` is reserved: with admission control there is no lossy path in v1, so it is never sent.
- An unreadable bot store is never repaired or replaced silently: the bot is unavailable (`503 bot_store_unavailable`
  for users, `503` at the socket) until an operator fixes the file.

## 6. Bot → hub requests

Every request carries `id` (`^[A-Za-z0-9._:-]{1,64}$`) and gets exactly one `res` with the same `id`. Fields not
listed are rejected (`invalid_request`, or `unsupported` for the reserved names in section 1).

| `t` | Fields | Result |
|---|---|---|
| `message.send` | `chat_id`, `text`, `format`? (`markdown` default, or `text`), `reply_to`?, `final`?, `idempotency_key`? | `{ "message_id", "chat_id", "date" }` |
| `message.edit` | `chat_id`, `message_id`, `text`, `format`?, `final`?, `idempotency_key`? | `{ "message_id", "chat_id", "edited": true }` |
| `message.delete` | `chat_id`, `message_id`, `idempotency_key`? | `{ "message_id", "chat_id", "deleted": true }` |
| `chat.action` | `chat_id`, `action` (`typing` only) | `{}` |
| `commands.set` | `commands`: `[{ "name", "description" }]` | `{ "count" }` |
| `models.set` | `providers`: `[{ "slug", "name"?, "current"? / "is_current"?, "models"? }]` | `{ "count" }` |
| `ack` | `event_id` (`id` optional) | `{ "acked" }` |
| `ping` | (`id` optional) | `pong` frame |

Rules:

- `chat_id` / `message_id` / `reply_to` must name a chat or message in **this bot's** store; anything else (another
  bot's, another account's, made up, or a string of the wrong shape) is `not_found`; a missing or non-string id is
  `invalid_request`. `reply_to` must be in the same chat.
- `message.edit` / `message.delete` only touch **bot-authored** messages: a user's message in the same chat is
  `forbidden`. A deleted message is `not_found`.
- `text`: string, 1 … 65 536 **UTF-8 bytes**, no NUL; larger is `too_large`.
- `commands.set` replaces this bot's command list: ≤ 100 entries, `name` `^[a-z0-9_]{1,32}$` (unique), `description`
  1 … 256 characters without control characters. They are published to the bot's users through
  `GET /api/agents/:name/commands` as plain chat commands (text the user sends; the bot decides what they do).
- `models.set` replaces this bot's provider catalog (WebSocket only; `id` required). ≤ 60 providers, each with
  `slug` `^[\w.:-]{1,64}$`. Optional `name` is trimmed to at most 80 characters with no control characters (blank or
  omitted uses `slug`). Optional `models` is at most 300 ids `^[\w.:/@+-]{1,200}$`; a missing or non-array `models`
  becomes `[]`. An id may be a string or an object with `id` or `name`. Extra fields on a provider or model object
  are ignored. `current` is true when `current` or `is_current` is boolean true — metadata only; this call does not
  spend, switch, or authorise a model. An empty `providers` list clears. Users see the list at
  `GET /api/agents/:name/models` as `{ "mode": "bot", "providers" }`. Not available over `POST /api/bot/rpc`.
- `chat.action` is transient (not stored); users following the chat see `event: foxfleet.bot` `{"action":"typing"}`.
- `final: true` tells the hub the reply in this chat is complete (ends the user's live run, section 7).
- Rate: a token bucket per bot (default 60 requests burst, 20/s refill), shared by all of the bot's connections;
  `ack`, `ping` and `pong` are not counted on the socket. Over the limit: `rate_limited` with `retry_after_ms`, no state change.
  Over HTTP every authenticated request (including `ping`, `ack`-shaped or unsupported frames) costs one bot token before its
  body is read, so malformed or oversized bodies are bounded too.
- `id` is required on every request except `ack`, `ping` and `pong`. An `ack` at or below the current ack answers
  `{"acked": N}` with the value sent and changes nothing.

### Idempotency

- Scope: (bot, operation, `idempotency_key`), key `^[A-Za-z0-9._:-]{1,128}$`. The record holds a fingerprint (SHA-256)
  of the canonical request (operation + every field except `id`/`idempotency_key`) and the result.
- The record is written in the same atomic store write as the effect, before `res` is sent; it survives reconnects
  and hub restarts.
- Same key, same payload → the stored result again, with the **new** request `id` and `"replayed": true`; no second
  effect. Same key, different payload → `idempotency_conflict`, no effect.
- Retention: the newest 5 000 records per bot, at most 24 h; older keys may be processed again.

### Error codes

`invalid_request`, `unsupported`, `unknown_type`, `bad_frame`, `not_found`, `forbidden`, `too_large`, `rate_limited`,
`idempotency_conflict`, `ack_out_of_range`, `internal`.

## 7. User side (existing routes, bot agents)

All routes are the ones the apps already use, scoped to the signed-in account. For a bot agent none of them ever
contacts a dashboard, API server, connector or machine. In `server/index.js` a single branch, taken right after the
agent lookup and before every other agent route, sends every `/api/agents/:name/...` request for a bot to the bot
module; anything it does not implement is `404` (or `503 bot_disabled` with the flag off). Only `pin` falls through to
the shared hub-side handler.

- **Agent list/detail**: `status` `ready` when the bot is connected, otherwise `offline`; `online`/`chatReady` follow
  the socket. `capabilities`: `chat`, `sessions`, `bot: true`, `busy: ["queue"]`; `images`, `files`, `screen`,
  `voice`, `skills`, `reactions`, `agentReactions`, `nativeUi`, `nativeRuns` are `false`. `checks.bot` says connected /
  waiting (messages are queued) / no token / disabled.
- **Sessions** = bot chats (`chat_id` = `session_id`, `fc_…`): `GET /sessions` (newest first, `limit`, `offset`, `q`),
  `POST /sessions` `{title?}` → `201 {id, session_id, title}`, `GET /sessions/:id/messages` (pages counted from the end;
  `{id, role: user|assistant, content, ts, edited?}`), `PATCH /sessions/:id` `{title}`, `DELETE /sessions/:id`.
- **Send**: `POST /messages` and `POST /chat` take the current body
  `{ messages: [{role, content}], session_id?, client_id?, mode? }`. Only the newest user message is used; images or
  files are refused (`400 unsupported`) rather than dropped. No `session_id` creates a new chat. The chat, the
  message and the `message.new` event are written to disk in one store write **before** the response.
  - `/messages` → `202 { message: {id, state: "queued", mode: "queue", ack: "queued", text, created, session_id},
    session_id, run_id?, bot: {online} }`. Same `client_id` and text again → `200` with the same ids and
    `duplicate: true`; same `client_id` with other text → `409 client_id_conflict`. Same `client_id` and text with a
    different explicit `session_id` → `409 client_id_conflict` as well. A retry without `session_id` returns the chat
    first assigned (`/chat` streams that chat). If that chat was deleted, retrying its retained `client_id` is
    `404 Unknown session` on both `/messages` and `/chat`: it never acknowledges an orphan or opens a phantom run.
    A changed payload/session still conflicts (`409`); expired records follow normal retention rules.
    `client_id` records are kept 24 h (at most 5 000 per bot), then expire.
  - `/chat` → the run's SSE stream (`X-Hermes-Session-Id` = chat id), same admission.
  - Offline bot: the message is stored and queued; the response says `bot.online: false`. It is delivered when the
    bot connects. There is no fallback to any other transport.
  - `mode` is accepted for compatibility and always means `queue`.
- **Replies** use the existing run stream (`GET /runs`, `/runs/:id/events`, `POST /runs/:id/stop`). A run per chat is
  opened when a user message is accepted, or when the bot **sends** a new message to a chat that has none (an edit,
  delete or typing with no live run changes only the transcript and opens nothing). It starts with
  `event: foxfleet.bot` `{"bot":"online"|"offline"}` and carries
  `data: {"choices":[{"delta":{"content":…}}]}` for new text, `event: foxfleet.replace` `{"text": <whole reply>}` when
  the bot edits or deletes a message of the reply (send-then-edit streaming replaces the bubble instead of appending),
  `event: foxfleet.bot` `{"bot":"online"|"offline"}` / `{"action":"typing"}`, and ends with `data: [DONE]` after
  `final: true`, after 30 s without bot activity once the bot has written, or after 5 minutes without any. The
  persisted transcript stays the source of truth. A run that is stopped (chat or agent deleted, hub shutdown, or a
  confirmed 1.1 Stop) also gets the usual `event: foxfleet.run` `{"state":"stopped"}`. Edits or deletes of bot messages
  that are not part of the live run reach users only through the transcript. On `foxfleet.bot/1`, Stop does **not** end
  the run: `POST /runs/:id/stop` returns `confirmed: false` and the reply keeps going. There is no way to interrupt a
  1.0 bot. A 1.1 bot is interrupted only as described below.
- `GET /queue` → `{items: [], recent: [], halted: false, active_run, modes: ["queue"], open_requests: [], can_cancel: false}`.
- `GET /commands` → `{source: "bot", busy: ["queue"], commands}`: the bot's `commands.set` list
  (`handler: "chat"`, `executable: true`, `verified: false`) plus the app's own client commands. Never the bundled
  Hermes TUI list.
- `GET /models` → `{mode: "bot", providers}`: the bot's `models.set` catalog. Metadata only; it does not spend or
  switch a model.

### Stop (`foxfleet.bot/1.1`)

A bot that offers `Sec-WebSocket-Protocol: foxfleet.bot.v1.1, foxfleet.bot.v1` is answered with the highest version
this hub speaks. `foxfleet.bot.v1` alone still gets today's `hello` (`protocol: "foxfleet.bot/1"`, no `features`).
A 1.1 hello is `protocol: "foxfleet.bot/1.1"` plus `features: ["stop", "cards", "media"]`.

`POST /runs/:id/stop` on a live run whose bot is connected at 1.1 sends one transient frame and waits:

```
hub → bot   {"t":"chat.stop","stop_id":"fs_<16>","chat_id":"fc_…","user":{"id","name"},"date":ms,"expires_at":ms}
bot → hub   {"t":"callback.answer","id":"…","callback_id":"fs_…","outcome":"stopped"|"idle"|"refused"|"expired"}
            → {"t":"res","id":"…","ok":true,"result":{}}
```

- `chat.stop` has no `event_id`. It is not stored, not acknowledged and not replayed. A reconnect cannot deliver a
  stale stop.
- At most one stop is outstanding per chat. A second `POST` joins that wait and does not send another frame.
- `expires_at` is 10 seconds after the send. `stopped` or `idle` ends the view (`confirmed: true`,
  `state: "stopped"`). `refused`, `expired`, a timeout, or no 1.1 socket throws inside the existing
  `stopAndWait` contract: `confirmed: false` and the run stays.
- `callback.answer` is still reserved on a 1.0 socket (`unsupported`). On 1.1 it answers only the outstanding stop
  of **this** bot. A second, late, foreign or unknown `callback_id` is `not_found` and ends nothing. It is not
  available over `POST /api/bot/rpc`.
- The user on the frame is the account user who tapped Stop. The bot applies the same allowlist as a normal message
  and refuses anyone else. It feeds `/stop` through Hermes' own command path. An already-expired frame is answered
  `expired` and is not dispatched.

### Cards (`foxfleet.bot/1.1`, feature `cards`)

`card.send` and `card.close` are still reserved on a 1.0 socket and over `POST /api/bot/rpc` (`unsupported`). On 1.1 the hub mints the ids. A client-supplied id authorises nothing.

```
bot → hub   {"t":"card.send","id":"…","chat_id":"fc_…","kind":"approval"|"confirm"|"clarify","instance":"…"}
            → {"t":"res","id":"…","ok":true,"result":{"request_id":"frq_<16>","expires_at":ms}}
bot → hub   {"t":"card.close","id":"…","request_id":"frq_…"}   or   {"all_except_instance":"…"}
            → {"t":"res","ok":true,"result":{"closed":n}}
user → hub  POST /api/agents/:name/native/sessions/:chat_id/requests/:request_id
hub → bot   {"t":"callback","callback_id":"fcb_<16>","request_id":"frq_…","chat_id":"fc_…","user":{"id","name"},"kind":"…","value":{…}}
bot → hub   {"t":"callback.answer","id":"…","callback_id":"fcb_…","outcome":"resolved"|"expired"|"refused"}
```

- The web already renders these. Confirm is sent to the web as `kind: "approval"` (that UI has Once and Deny). The bot still receives `kind: "confirm"`. Deny on a confirm card means cancel.
- A tap is accepted only when the request is open, unexpired, in that chat, on that bot, and the result is `{choice: once|deny}` or `{answers: {question id: text}}`. The account user who tapped is the user on the callback. A user id in the body is ignored.
- A second tap, a wrong chat, a wrong bot, a forged choice, or an expired card is refused. The first accepted tap does not send a second callback.
- `callback` has no `event_id` and is not a transcript event. It is stored until `callback.answer`, and replayed on the next hello if that answer never arrived. A stop id and a card id cannot answer each other.
- While any card in the chat is open, that chat's reply run does not idle out.
- `all_except_instance` closes this bot's open cards from any other instance. Closing an unknown id closes nothing and is not an error.

### Retention (per bot)

At most 500 chats (`409 bot_chat_limit` beyond), the newest 2 000 messages per chat (older ones are pruned, oldest
first), unacknowledged events without limit below `max_unacked`, idempotency and `client_id` records as in section 6.
The chat, message and unacknowledged-event caps are configurable (`botOptions` `maxUnacked`, `maxChats`,
`maxMessagesPerChat`; positive integers, an invalid value refuses to start the hub); the defaults above apply when they
are omitted. The store is one private JSON file per bot (`<account dir>/bot/<botId>.json`, mode 0600), written atomically
(temp file, fsync, rename, then a best-effort fsync of the parent directory on POSIX), with all writes for one bot
serialized. On a filesystem without directory fsync a power loss right after a write may lose that last write: the store
is not claimed to be crash-durable there.

### Media (1.1)

A 1.1 `hello` advertises `media` and `limits.max_media_bytes` when HTTP media routes are enabled.
Bytes use HTTP with `Authorization: Bot <token>`. `media.upload` remains unsupported on WebSocket,
and all v1 reserved fields stay reserved on 1.0 sockets and HTTP RPC.

Upload to the exact `POST /api/bot/media` path (no query), with raw bytes,
`X-Foxfleet-Chat: <chat_id>` and optional `X-Foxfleet-Name`. The response includes
`media_id` (also `id`), `kind`, `mime`, `name`, `size`, `sha256`, and `expires_at`.
The hub sniffs bytes, forces a safe extension, and refuses unrecognized formats, HTML, SVG and executables.
Ambiguous containers use their generic class (for example, Office ZIP containers become `.zip`).
The default per-file cap is 25 MiB (`botOptions.maxMediaBytes`); the per-bot disk quota is 1 GiB
(`botOptions.mediaQuotaBytes`). Known oversized bodies are refused before streaming; failures remove blobs.
Unreferenced uploads expire after one hour. Chat, bot and account deletion remove their media.

A 1.1 socket can `message.send` with `media: [media_id, ...]` (1–10) and `text: ""`.
Every upload must belong to that bot and chat; missing, foreign or expired ids return `not_found`
and attach nothing. Existing idempotency rules apply. `GET /api/bot/media/:id` serves only that
bot's bytes, supports Range, uses `Cache-Control: no-store`, and sends `application/octet-stream`
with the sniffed type in `X-Foxfleet-Mime`. No bot-provided URL is fetched by the hub.

User messages to a connected 1.1 bot may contain at most four strict base64 `image_url` data parts.
The hub stores bytes on disk and sends `message.new.media: [{id, kind, mime, name, size}]`.
A 1.0 connection receives attachment text lines instead, with no media array, and rejects new image input.
Plugins download these ids into their own media cache before handing local paths to Hermes.

Bot replies expose attachments as `MEDIA:/bot-media/<id>/<safe-name.ext>` in transcripts and live replies.
This is a hub namespace. An account's `POST /api/agents/:name/media {ref}` resolves only attachments
in that bot's messages to a short-lived, account-bound `/api/media/<token>` URL.

## 8. Groups (foxfleet.bot/1.2)

Release A adds **groups before channels**, and groups only. A room is one conversation with one human owner;
agents belong to that account. Routing is mention/reply-driven: there is no `@everyone` and no automatic leader.
Serial agent turns. A multi-target human request queues in stable agent-id order. A bounded handoff chain has
at most **4 dispatches** per root and a **5-minute** (`300000` ms) chain deadline. New members may read all retained
room history. Nothing here changes global models, profiles, permissions or memory policies.

The machine-readable single source is `contract/rooms-frames.schema.json` (JSON Schema 2020-12 plus the
`invariants` list). `contract/bot-frames.vectors.json` has the accepted and rejected examples in its additive
`rooms` block. This section, and that schema, are what the hub, plugin, web and Android build against.

### Negotiation and features

Protocol `foxfleet.bot/1.2`, subprotocol `foxfleet.bot.v1.2`. A 1.2 client offers all three subprotocols:

```
Sec-WebSocket-Protocol: foxfleet.bot.v1.2, foxfleet.bot.v1.1, foxfleet.bot.v1
```

The hub selects the highest it supports: `foxfleet.bot.v1.2` > `foxfleet.bot.v1.1` > `foxfleet.bot.v1`. A 1.2 client
therefore still connects at 1.1 to an old hub. Old clients never offer v1.2, so they never receive group frames.
A 1.2 `hello` is:

```json
{ "t": "hello", "protocol": "foxfleet.bot/1.2", "bot": "<botId>", "resume_from": 41, "latest_event_id": 44,
  "heartbeat_ms": 25000,
  "features": ["stop", "cards", "media", "groups"],
  "limits": { "max_frame_bytes": 1048576, "max_text_bytes": 65536, "window": 100, "max_unacked": 1000,
    "max_mentions": 64, "max_actor_name_chars": 256, "max_conversation_title_chars": 256,
    "max_room_members": 100, "max_handoff_dispatches_per_root": 4, "handoff_chain_ttl_ms": 300000,
    "max_rooms": 500 } }
```

Group frames exist only on a negotiated 1.2 socket whose features include `groups`. `POST /api/bot/rpc` stays the
DM/text subset: there are no groups over HTTP in Release A. The user-side conversation routes are in
`contract/openapi.json` (`/api/conversations`, `/api/conversations/{id}`, members, messages, stop, resume, read,
preferences).

### Identity carriers

Room id, thread id, chat type and the authenticated actor travel in frame/source fields, never in
`event.metadata` (native admission has a closed metadata contract):

| field | value |
|---|---|
| `chat_id` | room id, same `fc_` grammar as a DM chat (`^fc_[A-Za-z0-9_-]{16}$`) |
| `thread_id` | stable room-scoped thread, `fcr_` + 16 URL-safe characters; with `chat_type: "group"` this yields one shared session per agent with zero global config change |
| `chat_type` | `"group"` |
| `message_id` | `fm_` + 16 URL-safe characters |
| `dispatch_id` | `fd_` + 16 URL-safe characters |
| `stop_id` | `fs_` + 16 (unchanged) |
| card ids | `frq_` request, `fcb_` callback (unchanged) |

Rooms are addressed by `chat_id`. `group_id` and `thread_id` stay **reserved fields** on `message.send` /
`message.edit` under 1.2 as well; a client never sends either on a send.

An `actor` is the authenticated sender and is always filled by the hub, never trusted from a request body:

```json
{ "kind": "human", "id": "<hub account id>", "name": "<username>", "is_bot": false }
{ "kind": "agent", "id": "agent:<agentId>", "name": "<display name>", "is_bot": true }
```

`kind` is `human` or `agent`. An agent actor always has `is_bot: true` and an `agent:<agentId>` id; a human actor
always has `is_bot: false` and a hub account id. Agent-origin messages are admitted as bot senders
(per-profile `FOXFLEET_ALLOW_BOTS=mentions`, owner-approved) with `user.id = "agent:<id>"`, `is_bot = true`, and
`allow_gateway_control = false`. The authenticated `kind` is what lets the plugin enforce owner-only cards and stop.
`actor.name` is 1 … 256 printable characters.

### Mentions

`mentions` is an array of typed agent entities (0 … 64 entries). Each entity is:

```json
{ "kind": "agent", "id": "agent:<agentId>", "offset": 6, "length": 11 }
```

`offset` and `length` are **UTF-16 code units** into `text` (the same units as JavaScript string indices and
Android/Java `String`), not Unicode scalar values or bytes. `0 <= offset`, `1 <= length`, and
`offset + length <= text.length`. A span never starts on a low surrogate or ends on a high surrogate, so a
surrogate-pair emoji (for example `🤖`) is covered by both code units. Spans do not overlap. Every id names an agent
member of that room; an unknown id, a non-member, a malformed id or a bad span is refused (`not_found` or
`invalid_request`) and the message is not stored.

### Frames

Hub → bot, room variants (existing 1.0/1.1 frames are byte-identical):

```json
{ "t": "message.new", "event_id": 45, "chat_id": "fc_…", "chat_type": "group", "thread_id": "fcr_…",
  "message_id": "fm_…", "actor": { "kind": "human", "id": "…", "name": "owner", "is_bot": false },
  "mentions": [{ "kind": "agent", "id": "agent:researcher", "offset": 6, "length": 11 }],
  "text": "hello @researcher", "date": 1760000000000, "reply_to"?: "fm_…" }
```

`reply_to` must name an `fm_` message committed in this same room; a reply to another room is `not_found`.
`message.new` is a durable event, acknowledged and replayed exactly like a DM event.

```json
{ "t": "chat.member", "event_id": 46, "chat_id": "fc_…", "chat_type": "group", "thread_id": "fcr_…",
  "action": "join" | "leave",
  "actor": { "kind": "human", "id": "…", "name": "owner", "is_bot": false },
  "member": { "kind": "agent", "id": "agent:<id>", "name": "<display name>", "is_bot": true },
  "date": 1760000000000 }
```

Only the human owner changes membership; members are agents. A join gives the agent access to all retained room
history.

`chat.stop` and card `callback` keep the existing callback/answer pattern and add the room carriers plus an
authenticated actor:

```json
{ "t": "chat.stop", "stop_id": "fs_…", "chat_id": "fc_…", "chat_type": "group", "thread_id": "fcr_…",
  "actor": { "kind": "human", "id": "…", "name": "owner", "is_bot": false },
  "date": 1760000000000, "expires_at": 1760000010000 }
{ "t": "callback", "callback_id": "fcb_…", "request_id": "frq_…", "chat_id": "fc_…", "chat_type": "group",
  "thread_id": "fcr_…", "actor": { "kind": "human", "id": "…", "name": "owner", "is_bot": false },
  "kind": "approval" | "confirm" | "clarify", "value": { … } }
```

Stop and card taps are owner-only: an agent actor never satisfies an owner check. `callback.answer` for a room
carries the room too:

```json
{ "t": "callback.answer", "id": "…", "callback_id": "fs_…" | "fcb_…", "chat_id": "fc_…",
  "thread_id": "fcr_…", "outcome": "stopped" | "idle" | "refused" | "expired" | "resolved" }
```

A `fs_` id accepts only stop outcomes; an `fcb_` id accepts only card outcomes. The existing rules (one outstanding
stop per chat, 10-second expiry, first accepted tap wins) still apply.

Bot → hub, room variants:

```json
{ "t": "handoff.request", "id": "…", "chat_id": "fc_…", "thread_id": "fcr_…",
  "source_message_id": "fm_…", "target_agent_id": "agent:<id>", "text": "please take this",
  "idempotency_key"?: "…" }
```

`handoff.request` is the plugin-registered, room-scoped handoff tool. The hub authenticates the bot token,
attributes the dispatch to that agent, checks the committed `source_message_id` is in this room, applies the
chain limits (4 dispatches per root, 5 minutes), and fans out. It is **not** `inject_message`. On success the result
is `{ "dispatch_id": "fd_…", "chat_id", "target_agent_id", "root_id", "depth", "deadline_at" }`
(`handoff_limit` / `handoff_expired` otherwise).

```json
{ "t": "chat.get", "id": "…", "chat_id": "fc_…", "thread_id": "fcr_…" }
{ "t": "chat.cancel", "id": "…", "chat_id": "fc_…", "thread_id": "fcr_…", "dispatch_id": "fd_…" }
```

`chat.get` reads one room's committed state; `chat.cancel` cancels a queued dispatch before it starts. Under 1.0
and 1.1 validators all three of `chat.member`, `chat.get` and `chat.cancel` stay reserved (`unsupported`); they
become real only under the 1.2 validator, the same pattern as `validateStopAnswer` for 1.1.

`message.send`, `message.edit`, `message.delete` and `chat.action` keep their 1.0/1.1 fields in a room and add an
optional `mentions` array; `group_id` and `thread_id` remain reserved. Room `card.send` / `card.close` add
`actor_kind: "agent"` (cards are authored by an agent; a human value is `forbidden`). `ack`, `ping`, `pong`,
`res` and `error` are unchanged.

### Limits

Reused bounds are unchanged: frame 1 MiB (`max_frame_bytes` 1048576), text 64 KiB (`max_text_bytes` 65536), the
100-event window, 1000 unacked events, and the existing id regexes. Groups add:

| limit | value | meaning |
|---|---|---|
| `max_mentions` | 64 | typed mention entities per message |
| `max_actor_name_chars` | 256 | printable characters in `actor.name` |
| `max_conversation_title_chars` | 256 | printable characters in a conversation title |
| `max_room_members` | 100 | agent members per room |
| `max_handoff_dispatches_per_root` | 4 | dispatches in one chain (at most 4 dispatches) |
| `handoff_chain_ttl_ms` | 300000 | 5-minute chain deadline |
| `max_rooms` | 500 | rooms per account |

Rejected group frames use the existing protocol codes `invalid_request`, `not_found`, `forbidden`, `unsupported`
and `too_large`. A group frame on a v1.1 socket is `unsupported`.
